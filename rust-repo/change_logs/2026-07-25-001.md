## Client OffsetAllocator persistence parity

The Rust client `OffsetAllocatorStorageBackend` now implements the observable
restart contract introduced by the C++ oracle without linking or calling the
C++ Store:

- `Disabled` remains the default, while `Relaxed` and `Strict` use the C++
  environment names, interval rule, and CRC disable spellings.
- New writes use the 24-byte little-endian v3 logical header, a 4 KiB-aligned
  value, nonzero monotonic write sequence, known flags, and optional CRC-32C
  over the header prefix, key, and value.
- Checkpoints use a checksummed versioned Rust envelope and atomically publish
  temporary-file write, file sync, rename, and parent-directory sync after an
  arena durability barrier. Failed publication retains dirty retry state.
- Recovery validates checkpoint and record metadata transactionally. Torn,
  corrupt, overlapping, out-of-range, unknown-format, mismatched, or
  post-checkpoint records are isolated; survivors rebuild extent and FIFO
  state deterministically. Sorted overlap validation is linear after the
  initial sort, so large checkpoints do not trigger a quadratic scan.
- Legacy JSON indexes and raw-value records remain readable beside new v3
  records. New checkpoints do not rewrite legacy arena bytes in place.
- Reads pin an extent and open its arena file under the state lock, then copy
  without holding that lock. Delete, replacement, eviction, and `remove_all`
  cannot reuse or unlink an in-flight reader's bytes prematurely.
- One live backend owns each data directory through an advisory lock.
  `remove_all` preserves strict empty-checkpoint ordering and relaxed
  old-or-new generation semantics.
- Only finalized evictions become tombstones. Rollback creates none, rewrite
  clears stale tombstones, and strict/relaxed checkpoint failures remain
  retryable according to their mode contracts.
- Version-2 checkpoint entries authenticate the expected record flags, so an
  arena edit cannot disable CRC verification for a checksummed record.
- Relaxed recovery starts its next interval at successful recovery time rather
  than checkpointing the first post-restart mutation immediately.

## Intentional differences and limits

- Rust checkpoints serialize `PersistedIndex` and reconstructed free extents;
  they do not serialize the C++ allocator tree. The checkpoint envelope is
  Rust-owned and does not change protobuf or C++ formats.
- Pre-feature Rust checkpoints may contain headerless raw values. They remain
  readable with their original offsets, but retain their legacy integrity
  limits rather than gaining synthetic v3 checksums.
- Every successful record write currently calls `sync_data`, including
  Disabled and Relaxed modes. This is stronger durability than required before
  a checkpoint and has an acknowledged performance cost.
- Graceful `Drop` makes a best-effort final checkpoint and cannot return an
  error to its caller. Strict public mutations still return durability errors.
- Abrupt-restart coverage uses a logical hook that suppresses `Drop`; it proves
  protocol state transitions but is not a real power-loss, filesystem-cache,
  or storage-hardware test.
- The master crate's append-only `StorageBackendType::OffsetAllocator`
  snapshot adapter is a separate surface and was intentionally not changed.
- `OffsetAllocatorConfig` retains its pre-feature public field layout, so
  exhaustive external struct literals remain source compatible. The separate
  `OffsetPersistenceConfig` supports explicit mode, interval, and record-CRC
  selection through `new_with_persistence`; `new(config)` reads the matching
  C++ environment variables.
