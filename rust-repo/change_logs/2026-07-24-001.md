# Migration Log 2026-07-24-001

Status: Completed

Baseline: `2a58bac5`

## Canonical TenantId parity

### Upstream

- `c45fb07c` establishes a validated C++ `TenantId` and carries it through the
  Store control plane.
- Empty tenant input selects `default` for ordinary requests. Strict write
  admission requires a non-empty, valid, registered tenant.
- Tenant IDs beginning with `_`, containing bytes below `0x20`, or containing
  byte `0x7f` are invalid. Printable punctuation and valid non-ASCII UTF-8 are
  accepted.
- When multi-tenant quota is disabled, request tenant fields are ignored and
  all operations address `default`.
- The scoped-key representation remains `tenant_id + NUL + local_key`.

### Rust migration

- Introduce a Store-owned `TenantId` domain type and carry it through object
  state, quota state, recovery, replication, promotion, offload, drain, task,
  and request-processing paths.
- Resolve each request tenant once before quota reservation, allocation, map
  mutation, task enqueue, or oplog append. Batch and nested-task requests
  prevalidate all tenant identities before processing their first item.
- Validate snapshot and oplog identities during recovery. Preserve opaque
  embedded NUL bytes in three-field C++ catalog user keys, parse only legacy
  two-field scoped keys, and reject conflicting oplog identities.
- Remove the unchecked legacy `normalize_tenant_id`,
  `make_tenant_scoped_key`, and `split_scoped_key` exports. Internal scoped-key
  creation and parsing now use `TenantId` methods.
- Keep copy, move, and drain task tenant identities typed until the JSON
  serialization boundary.

### Ping and remote-pull disposition

- The current C++ Ping path accepts only a client ID and has no tenant-domain
  behavior. Rust therefore ignores the compatibility `PingRequest.tenant_id`
  field; an invalid-looking value does not reject or mutate tenant state.
- Remote-pull coordination has no same-named C++ API and is classified as a
  Rust-only compatibility surface. Applying the canonical identity contract,
  strict mode validates and scopes its coordination key by tenant, while
  disabled quota mode ignores the supplied tenant and uses `default`. This is
  an explicit inference, not a claim of direct C++ method parity.

## Full-chain boundary

Store-owned tenant identity is represented by `TenantId`. The remaining raw
string representations are intentional boundaries:

- protobuf and admin HTTP request/response fields;
- oplog JSON and snapshot/catalog string fields;
- KV-event compatibility output and deprecated KV-event configuration;
- tenant quota YAML/etcd configuration;
- logging, diagnostics, and user object keys.

`pending_remote_pulls` remains keyed by `String` because its key is the already
canonical tenant-scoped object key, not a standalone tenant identity.

## Wire and durable compatibility

- No protobuf type, field number, or RPC definition changed.
- Snapshot/catalog shapes and MessagePack field order are unchanged.
- Oplog JSON keys and string field shapes are unchanged.
- Tenant quota YAML/etcd formats are unchanged.
- Scoped-key bytes remain `tenant + '\0' + local_key`, splitting only the first
  NUL where the legacy format permits scoped-key parsing.
- Task JSON still serializes `tenant_id` as the same string because `TenantId`
  uses transparent serde serialization.
