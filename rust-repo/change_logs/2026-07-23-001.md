# Three-node Docker Soft-RoCE acceptance

The standard privileged E2E now provisions three manifest-owned RXE devices
on a software-RoCE bridge and runs three Transfer Engine plus three Rust Store
nodes. Direct TE validation covers A↔B, B↔C, and C↔A; all six directed paths
must select RDMA and compare byte-identically.

Rust Store acceptance uses explicit 3/2/1 replica profiles. The baseline gate
requires complete memory replicas on all three nodes. The degraded-read gate
starts with two owners, removes one, and verifies the remaining owner. The
multi-level gate uses one replica, proves `LocalDisk` fallback under memory
pressure, verifies bytes, and promotes to a complete healthy RDMA replica.

The resilience suite rotates failures across A/B/C and covers Store restart,
Master plus etcd restart with oplog recovery, RXE C disconnect/reconnect,
two-owner degradation, memory and SSD watermark eviction, mixed object sizes,
and a second clean standard pass. The Python extension uses the Rust Store
backend and does not load the C++ Store library.

The canonical command is:

```bash
CARGO_BUILD_JOBS=5 \
RDMA_ARTIFACT_ROOT=/home/fy2462/workspace/tmp/mooncake/rdma-multinode \
bash rust-repo/tools/rdma-multinode/run.sh all
```

Host setup, C-link interruption, and cleanup request interactive `sudo`; no
password is stored by the suite. Retained evidence lives in the shared artifact
root, test runtime data stays under container `/tmp`, and normal Cargo tests use
`rust-repo/target`. Open-RDMA remains an independent mock-only compatibility
check and is not counted as multi-node data-plane evidence.
