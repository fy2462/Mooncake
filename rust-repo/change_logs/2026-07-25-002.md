## Decode reconfigure make-before-break

### Upstream

Commit `592f117822adde8991d4577545ae3a4b0694f870` changes
`mooncake-wheel/mooncake/mooncake_store_service.py` so a decode-to-decode
replacement mounts the new segment before retiring the old segments. A failed
replacement preserves the prior decode capacity and mode; a successful
replacement tracks only old segment IDs whose individual cleanup failed.

The commit and its tests are already present on this branch through merge
`314560b2`.

### Rust compatibility-surface audit

The Rust wheel owns an independent, currently smaller REST implementation in
`rust-repo/python/mooncake_store/service.py`. Its public application currently
contains health and object CRUD routes only. It has no `/api/reconfigure`
route, no decode/prefill mode, no mounted-segment list, and no last-mount
state. Therefore there is no existing Rust state transition on which to apply
the ordering fix from `592f1178`.

The Rust PyO3 segment interface is also not a drop-in implementation of the
legacy service contract: Rust exposes asynchronous mount/unmount by segment
name and base address, while the legacy service calls synchronous path-based
mounting and tracks master-assigned UUIDs. Implementing `/api/reconfigure`
would require a new UUID-handle API plus shared-memory mapping, Transfer Engine
registration, overlapping-generation bookkeeping, and resource cleanup. That
is a new compatibility feature, not the bounded make-before-break correction
introduced by `592f1178`.

Disposition: do not add that new surface as part of this merge-parity slice.
The existing legacy Python service inherits and verifies `592f1178`. If the
Rust REST service later gains decode reconfiguration, make-before-break,
same-path replacement, failed-mount preservation, and per-ID cleanup must be
acceptance requirements for that feature rather than a follow-up fix.
